How it works 06 / 12

One WebSocket carries the voice; one Durable Object owns the state and fans it out.

01 Station browser + headset: 24 kHz PCM16 streams.
↓ input.audio, streamed as the cook speaks
02 AssemblyAI Voice Agent STT, turn detection, LLM + 10 tools, TTS.
↓ transcript → instant lane acts; LLM call deduped
03 Worker + Durable Object tokens, authoritative state, fan-out.
↓ state broadcast to every open socket
04 Every screen kitchen display, servers’ board, online menu.

Screens change on the broadcast, before the agent speaks.

Grammar first · LLM confirms Temp token, key stays server-side

What we tuned · 1 of 2 Detail

Sending tool results immediately cut two seconds of dead air from every confirmation.

What the docs suggested
Wait for reply.done before sending tool.result: the agent may be speaking a transition.
What the timelines showed
That transition is silent. We send tool.result immediately: confirmations ~2 s sooner, zero errors in any recorded session.
Measured and reverted: execution_mode hold · shorter prompt · min_silence 400 ms
Evidence: eval/results + recordings ← returns to results
What we tuned · 2 of 2 Detail

transcription_mode: min_latency bought 0.6-1 s at the same accuracy.

balanced mode · 3-command A/B2.85-4.3 s

Prompt fixes that landed: chatter gets silence, menu nicknames (“the fish” → salmon), number homophones, and a silent-reply gate.
